What this file is
-----------------
The exclusion constraint from Finding A closes the booking race, but it does not decide how
Postgres resolves the contention it creates. Usually: one insert commits and the rest raise
23P01. Sometimes the waiters form a cycle and Postgres resolves it as a deadlock instead.
BookAsync caught only 23P01, so those became 500s.

Every INSERT below is timed at almost exactly 1,002ms — Postgres's default deadlock_timeout
of 1s — so each waiter sat the full second before the detector fired.

  The chain is InvalidOperationException -> DbUpdateException -> PostgresException.
  BookAsync's clause was `catch (DbUpdateException e) when (e.InnerException is
  PostgresException { SqlState: 23P01 })`. It fails on both counts: the SqlState is 40P01,
  and the outer exception is not a DbUpdateException. Npgsql classifies deadlock as
  transient, so EF Core's execution strategy wraps it — InvalidOperationException with no
  retry policy configured, RetryLimitExceededException once a retrying strategy is out of
  attempts. Adding 40P01 to that same clause would still not have caught it.

How it was captured
-------------------
Server-side logs never reach scripts/dev-test.ps1's stdout — VSTest captures the app's
console output into the .trx and nowhere else, and the script removed the container, and
the .trx with it, in its finally block. This capture required a throwaway runner that kept
the container. `-KeepResults` was added to dev-test.ps1 afterwards so the next occurrence
of anything like this is readable without one.

The first fix made it worse
---------------------------
EF Core's EnableRetryOnFailure was tried first (maxRetryCount 5, maxRetryDelay 250ms). Its
execution strategy retries SaveChangesAsync alone, so every deadlock victim went straight
back to the INSERT without re-reading, and fifty of them re-contended on the constraint in
waves. Captured on run 14 of a 25-run verification loop:

  Command failures, by duration (top 5) — no longer deadlock_timeout, now CommandTimeout:

  slow lock convoy.

Fix
---
A bounded retry inside ReservationService.BookAsync that re-reads before it re-inserts, so a
victim normally finds the winner's row and returns 409 without touching the constraint again.
Jittered delays, three attempts, and 503 with Retry-After if they are exhausted. No
EnableRetryOnFailure, and no change to any other write path. See DECISIONS.md section 7.
