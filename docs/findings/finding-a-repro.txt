What this file is
-----------------
The recorded failure of a concurrency test committed *before* the fix exists. The
test is committed skipped and fails the moment it is un-skipped.

The ordering is the point. A concurrency test written after a fix proves nothing:
nothing establishes that it ever exercised the race, so it may have passed on the
first run for reasons unrelated to the change. Committed first and shown failing,
it becomes the thing the fix has to turn green.

What fails
----------
ReservationService.BookAsync checks for an overlapping reservation with a SELECT
and then INSERTs, with no transaction and no lock:

    src/LabQueue.Core/Services/ReservationService.cs
      79   var conflict = await db.Reservations.FirstOrDefaultAsync(...)
      85   if (conflict is not null) -> 409
     103   db.Reservations.Add(reservation);
     104   await db.SaveChangesAsync(ct);

Under READ COMMITTED every request whose SELECT runs before some other request has
committed its INSERT sees an empty result, concludes the slot is free, and inserts.
The check and the act are not atomic, and nothing in the schema refuses the second
row: `reservations` carries a primary key and EF Core's two foreign-key btrees, and
no uniqueness or exclusion constraint over (resource_id, during).

Fifty requests released together therefore do not produce one booking and
forty-nine conflicts. They produce as many bookings as fit inside the window
between the first SELECT and the first committed INSERT.

Why the numbers vary
--------------------
The count is not a property of the bug, it is a property of how many requests get
their SELECT in before the first INSERT commits. That depends on scheduling, so it
moves between runs. What is stable across all five runs is that it is never one.

Why the release spread is reported
----------------------------------
The failure is only meaningful if the fifty requests were genuinely simultaneous, so
the test records a timestamp on each thread the instant the barrier releases it and
reports the spread. A spread of roughly two milliseconds across fifty threads is
the requests actually overlapping.

It is reported for the opposite case too. If this test ever passes, the spread says
whether it passed because something in the schema stopped the race or because the
requests never raced at all — a test that cannot fail proves nothing, and a passing
run with a large spread is the second case wearing the first one's clothes.

What was deliberately not done
------------------------------
No delay was injected between the SELECT and the INSERT, and nothing was added to
the booking path to widen the window. The window measured here is the one the code
has. Costs that would otherwise land on whichever requests happened to go first —
JIT, EF Core query compilation, opening Npgsql connections — are paid before the
barrier, which tightens the release rather than widening the window.

Three things that would make this test pass for the wrong reason were avoided in
the fixture: a shared transaction across requests, a connection-pool ceiling below
fifty, and awaiting the fifty calls in a loop. Each serialises the requests. The
fixture opens no transaction, sets no MaxPoolSize, and releases fifty dedicated
threads from a Barrier.
