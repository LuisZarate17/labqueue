Method
------
Parameters are literals, not bind parameters, so the plan shown is a custom plan
and not a generic one. A warm-up execution is run and discarded before the
measured run.

On buffer accounting: the reservations heap is 57 MB against a shared_buffers of
128 MB, which puts it over the 32 MB (shared_buffers / 4) threshold at which
Postgres switches sequential scans to a 256 KB bulk-read ring buffer. The table
is therefore NOT retained in shared_buffers between scans, which is why the plan
below reports "read" rather than "hit" even on a repeated run. Those reads are
served by the OS page cache rather than the disk. This is ordinary behaviour for
a table of this size and it is stable across runs, so before/after comparisons
are valid; it is recorded here because the raw buffer counts look like cold I/O
and are not.
