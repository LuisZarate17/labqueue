What this baseline is
---------------------
The schema carries the indexes EF Core creates on its own: a btree on every
foreign key, including reservations.resource_id. That is what a reservation API
written with EF Core looks like by default, and it is the baseline Finding B is
measured against.

An earlier capture removed ForeignKeyIndexConvention, which produced a sequential
scan and a much larger apparent improvement. That was rejected: suppressing an
index the ORM would have created makes the "before" number a property of the
measurement setup rather than of the code, and it inflates the result by folding
"no index at all" into what is meant to be a claim about range indexing.

So there are three states, and only the second delta is Finding B:

  1. no index at all              — not shipped; artificial, requires disabling a convention
  2. btree on resource_id         — THIS FILE. What EF Core gives you by default
  3. gist (resource_id, during)   — the phase 06 fix

The interesting result is that the query is already using an index here and is
still doing far too much work: the bitmap index scan finds 2,454 rows for the
resource, and the heap filter then discards 2,431 of them to return 23. The
resource is selective; the time window is not indexed at all. That is the finding.

On buffer accounting: with the foreign-key index in place the measured run reports
shared hit throughout — the bitmap scan touches 2,453 buffers and stays inside
shared_buffers. The earlier seq-scan baseline reported "read" because a 57 MB heap
exceeds the 32 MB (shared_buffers / 4) threshold at which Postgres switches
sequential scans to a 256 KB bulk-read ring buffer and stops retaining the table.
That no longer applies to this plan, and is recorded only because it explains the
difference against the previous capture.

Method
------
Three forms of the same query are captured: the literal form the plan document
specifies, and the statement EF Core actually emits under both plan_cache_mode
settings, because the application sends bind parameters rather than literals. All
three agree on plan shape and time, so the custom-vs-generic question is settled
rather than assumed. A warm-up execution is run and discarded before the measured
run.
