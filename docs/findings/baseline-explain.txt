This is state 1 of the three-state measurement: no index on reservations at all.
States 2 (btree on resource_id) and 3 (GiST on resource_id + during) are measured
in phase 06 against this same seed. The seed derives every key from md5() of a
stable string and anchors its timeline to fixed dates, so a full teardown and
reload reproduces it exactly: verified at 500,942 confirmed / 9,973 cancelled /
739 maintenance windows across two independent loads.

Method
------
Two forms of the same query are captured. The first uses literals, which is the
form the plan document specifies. The second is the statement EF Core actually
emits, run through PREPARE/EXECUTE under both plan_cache_mode settings, because
the application sends bind parameters rather than literals and a generic plan can
differ from a custom one. The column lists are equivalent: EF names all seven
columns, which is "SELECT *" in all but spelling.

A warm-up execution is run and discarded before the measured run.

On buffer accounting: the reservations heap is 57 MB against a shared_buffers of
128 MB, which puts it over the 32 MB (shared_buffers / 4) threshold at which
Postgres switches sequential scans to a 256 KB bulk-read ring buffer. The table
is therefore NOT retained in shared_buffers between scans, which is why the plans
below report "read" rather than "hit" even on a repeated run. Those reads are
served by the OS page cache, not the disk. This is ordinary behaviour for a table
of this size and it is stable across runs, so before/after comparisons remain
valid; it is recorded because the raw buffer counts otherwise look like cold I/O.
