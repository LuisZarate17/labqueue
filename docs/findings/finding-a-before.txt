What happens
------------
ReservationService.BookAsync SELECTs for an overlapping confirmed reservation and then
INSERTs if it found none. Nothing holds the gap between the two statements — no
transaction, no lock. Under READ COMMITTED, the Postgres default and what EF Core gives
you, every concurrent caller reads the same empty result and every one of them inserts.

Query used, scoped to the one resource on purpose — unscoped it is a self-join over
500k rows with no index to help it and it does not return:

  SELECT a.id, b.id, a.during FROM reservations a JOIN reservations b
    ON a.resource_id = b.resource_id AND a.id < b.id AND a.during && b.during
  WHERE a.status='confirmed' AND b.status='confirmed' AND a.resource_id = '<target>';

On the conflict counter
-----------------------
reservations.conflicts.total does NOT move during this run, and that is the point rather
than a gap in the instrumentation: the counter increments when the overlap check rejects a
booking, and here it rejected nothing. The metric is flat because the bug is total. It
spikes to 49 after the fix — see finding-a-after.txt.

What this run is not
--------------------
k6 has no barrier primitive and VU startup staggers, so this is load shape and telemetry,
not the proof. The proof is the xUnit Barrier test in
tests/LabQueue.Tests/ConcurrentBookingTests.cs, which releases fifty in-process threads at
once and was recorded failing 5/5 in finding-a-repro.txt before this fix existed.
